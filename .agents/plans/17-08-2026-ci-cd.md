# Automatic Deploy Pipeline - Implementation Plan

> **For agentic workers:** use the `executing-plans` skill to work through this plan task by task.
> Steps use checkbox (`- [ ]`) syntax for tracking. Tick them as you go.

**Goal:** Every push runs the whole test suite in GitHub Actions; a green push to `main` migrates the
production database and then deploys both Vercel projects, backend first.

**Architecture:** One workflow file, `.github/workflows/ci.yml`, with six jobs. Three of them check
(`backend`, `frontend`, `e2e`) and run on every branch. Three of them ship (`migrate`, `deploy-api`,
`deploy-web`), gated on `github.ref == 'refs/heads/main'` and chained behind the checks with `needs`,
so a red suite never reaches Vercel. Builds stay remote: Actions calls `vercel deploy --prod` and
Vercel builds, exactly as the README's manual command does today. The only production code change is
in `frontend/playwright.config.ts`, which currently reads two `.env` files off disk that no runner
has.

**Tech Stack:** GitHub Actions, `astral-sh/setup-uv`, `actions/setup-node`, Vercel CLI, Alembic,
Neon branches.

**Spec:** `AGENTS.md`. It has no CI section yet - Task 5 writes one. Nothing in this plan changes the
application's behaviour, so the spec's requirements are untouched; what it gains is a record of how
the code reaches production.

## Decisions closed before planning

| Question                                          | Answer                                                                       |
| ------------------------------------------------- | ---------------------------------------------------------------------------- |
| Who triggers the deploy?                          | GitHub Actions, after the checks pass. Vercel's own Git integration must be off, or both would deploy the same push |
| Which suites gate it?                             | All of them: `ruff`, `pytest`, `eslint`, `tsc`, Vitest, and the full Playwright suite |
| Does the pipeline run `alembic upgrade head` on production? | Yes, in its own job, before the backend deploys                     |
| What happens on a branch push?                    | The three check jobs run. Nothing deploys                                    |

## Decisions taken while planning

Technical, reversible, and flagged so they can be revisited rather than rediscovered.

| Decision                                                     | Reason                                                                    |
| ------------------------------------------------------------ | ------------------------------------------------------------------------- |
| Vercel builds remotely; no `vercel build` / `--prebuilt`      | The gate is the job ordering, not where the build happens. `--prebuilt` would mean `vercel pull` writing `.vercel/` for two projects that both deploy from the repository root, and building a Python function locally on a runner - all to move build minutes from Vercel to Actions. `vercel deploy --prod` is the command the README already documents and the one known to work with these two projects |
| One workflow file, not two chained by `workflow_run`          | `workflow_run` fires on a separate event with no branch context of its own, and needs its own status wiring. `needs:` plus one `if:` reads top to bottom |
| A single global `concurrency` group, not one per branch       | `pytest` and Playwright both truncate the same Neon `test` branch. Two runs at once would delete each other's rows. `cancel-in-progress: false`, so a push to `main` queues behind a branch run rather than being killed by one. GitHub holds only one run pending per group, so three pushes in quick succession skip the middle commit's run entirely - the newest still runs and still deploys, which is the behaviour that matters |
| `pytest` and `e2e` are separate jobs, chained                 | Same reason. `e2e` declares `needs: [backend, frontend]`, which serialises the two DB users without a second Neon branch to create and pay for |
| CI migrates the `test` branch before `pytest`                 | A commit that adds a migration would otherwise fail against a stale test database. It also means every migration is applied twice - once to `test` on every push, once to production on merge - so a broken migration is caught on a throwaway database first |
| The login password, the auth secret and the API key are literals in the workflow | Both services under test are local to the runner and die with the job. They are configuration, not secrets. Keeping them out of the secret store means one less thing to rotate, and the file says plainly what it is doing. They must never match the real values |
| Vercel org and project IDs go in secrets anyway               | They are not credentials, but this repository is public and they name the account's internals. The cost is three more secrets to set once |
| `vercel@latest`, not a pinned major                           | A CLI break shows up as a failed deploy, never as a bad one, and one user does not need to babysit a version. If it ever breaks, pin the major in that one step |
| Nothing new in pytest or Vitest                               | No application logic changes. The pipeline's own test is that it runs, which is Task 2, 3 and 4's verification step |

### Task 1: Let the Playwright config run without `.env` files

`playwright.config.ts` calls `readFileSync("./.env.local")` and `readFileSync("../backend/.env")` at
module scope. A GitHub runner has neither file, so the config throws `ENOENT` before a single test is
collected. The fix is one guard: fall back to the process environment, which is where CI keeps the
same four values.

**Files:**

- [ ] **Step 2: Add the fallback**

```ts
/** Reads a .env file without pulling in a dependency just for the test config. A CI runner has no
 *  such file and passes the same names in its environment instead, so an absent file is not an
 *  error - it means the values are already here. */
function readEnv(path: string): Record<string, string> {
  if (!existsSync(path)) return process.env as Record<string, string>;

  const values: Record<string, string> = {};
```

- [ ] **Step 3: Write the workflow**

Create `.github/workflows/ci.yml`:

```yaml
name: CI

on:
  push:
  workflow_dispatch:

permissions:
  contents: read

# One group for the whole repository, not one per branch: pytest and the Playwright suite both
# truncate the same Neon test branch, so two runs at once would delete each other's rows. Queued
# rather than cancelled, so a push to main never loses its deploy to a branch push that arrived
# first.
concurrency:
  group: ci
  cancel-in-progress: false

env:
  # Throwaway CI values, not secrets. Both services under test are started by the runner, reachable
  # only from it, and die with the job. They must never match the real values in Vercel.
  BACKEND_API_KEY: ci-api-key
  APP_PASSWORD: ci-password
  AUTH_SECRET: ci-auth-secret-not-the-real-one-32-chars
  # AI_STUB replaces the OpenAI call, but app/config.py requires the variable to exist before
  # anything can import, so the backend needs a value here to start at all.
  OPENAI_API_KEY: ci-openai-key-never-called

jobs:
  backend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: backend
    env:
      # Both names, one branch. Alembic reads DATABASE_URL and app/config.py requires it; the test
      # suite reads TEST_DATABASE_URL. Pointing them at the same throwaway branch is the point:
      # nothing in this job may touch production.
      DATABASE_URL: ${{ secrets.TEST_DATABASE_URL }}
      TEST_DATABASE_URL: ${{ secrets.TEST_DATABASE_URL }}
    steps:
      - uses: actions/checkout@v7

      # Pinned to a full version: astral-sh/setup-uv publishes no floating major tag, so `@v10`
      # does not resolve.
      - uses: astral-sh/setup-uv@v10.0.1
        with:
          enable-cache: true

      - name: Install dependencies
        run: uv sync --frozen

      - name: Lint
        run: uv run --frozen ruff check .

      - name: Check the committed OpenAPI schema is current
        # openapi.json is committed and the frontend build generates its types from it, so a
        # Pydantic change that skipped the export would ship stale TypeScript that still compiles.
        run: |
          uv run --frozen python -m scripts.export_openapi
          git diff --exit-code -- openapi.json

      - name: Migrate the test database
        run: uv run --frozen alembic upgrade head

      - name: Test
        run: uv run --frozen pytest

  frontend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: frontend
    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-node@v7
        with:
          # Both Vercel projects build on 24.x. CI matches production rather than the newest LTS.
          node-version: 24
          cache: npm
          cache-dependency-path: frontend/package-lock.json

      - name: Install dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

      # PageProps and LayoutProps are globals Next generates into .next/types/routes.d.ts, which is
      # gitignored - so tsc passes locally off an old build and fails on a fresh checkout. typegen
      # writes them without paying for a full build.
      - name: Generate route types
        run: npx next typegen

      - name: Check types
        run: npx tsc --noEmit

      - name: Test
        run: npm test
```

> **Correction, made during execution.** Two things in this YAML were wrong on the first run, and both
> are the kind only CI can tell you.
>
> **`astral-sh/setup-uv@v10` does not resolve** - `Unable to resolve action, unable to find version
> v10`. That repository tags full versions and a few minors (`v7.6`) but no bare majors, unlike
> `actions/*`. It is pinned to `v10.0.1`. Check with `gh api repos/astral-sh/setup-uv/tags --jq
> '.[].name'` rather than assuming a major alias exists.
>
> **`npx tsc --noEmit` fails on a fresh checkout** with `TS2304: Cannot find name 'PageProps'` and the

> `.next/types/routes.d.ts`, which `.next/` being gitignored means no runner has. It passes locally

> run is exactly the thing to catch. `next typegen` writes those definitions without a full build, so
> it runs as its own step first.

`uv sync --frozen` and `uv run --frozen` both refuse to update `uv.lock`, so a lockfile that has
drifted from `pyproject.toml` fails the job instead of being silently fixed. `uv` provisions Python
3.13 itself from `requires-python`, which is why there is no `setup-python` step.

```yaml
  # frontend, so all three checks gate the deploy.
  migrate:
    runs-on: ubuntu-latest
    needs: [e2e]
    if: github.ref == 'refs/heads/main'
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v7

      # Pinned to a full version: astral-sh/setup-uv publishes no floating major tag, so `@v10`
      # does not resolve.
      - uses: astral-sh/setup-uv@v10.0.1
        with:
          enable-cache: true

      - name: Migrate production
        # alembic/env.py imports app.db, which imports app.config, which requires BACKEND_API_KEY
        # and OPENAI_API_KEY as well. Alembic never uses either; they only have to exist, and the
        # workflow-level throwaways are enough.
        run: uv run --frozen alembic upgrade head
        env:
          DATABASE_URL: ${{ secrets.PROD_DATABASE_URL }}

  deploy-api:
    runs-on: ubuntu-latest
    needs: [migrate]
    if: github.ref == 'refs/heads/main'
    env:
      VERCEL_ORG_ID: ${{ secrets.VERCEL_ORG_ID }}
      VERCEL_PROJECT_ID: ${{ secrets.VERCEL_PROJECT_ID_API }}
    steps:
      - uses: actions/checkout@v7

      - name: Install the Vercel CLI
        run: npm install -g vercel@latest

      # Deploys run from the repository root, not from backend/. Each project's root directory is
      # set on Vercel, and the frontend build reads backend/openapi.json from outside its own.
      - name: Link the project
        run: vercel pull --yes --environment=production --token=${{ secrets.VERCEL_TOKEN }}

      - name: Deploy
        # Waits for the remote build and exits non-zero if it fails, so the job status is the
        # deployment's status.
        run: vercel deploy --prod --yes --token=${{ secrets.VERCEL_TOKEN }}

  deploy-web:
    runs-on: ubuntu-latest
    # After the backend: a commit that changes the API contract must not put a frontend in front of
    # a service that cannot answer it yet.
    needs: [deploy-api]
    if: github.ref == 'refs/heads/main'
    env:
      VERCEL_ORG_ID: ${{ secrets.VERCEL_ORG_ID }}
      VERCEL_PROJECT_ID: ${{ secrets.VERCEL_PROJECT_ID_WEB }}
    steps:
      - uses: actions/checkout@v7

      - name: Install the Vercel CLI
        run: npm install -g vercel@latest

      - name: Link the project
        run: vercel pull --yes --environment=production --token=${{ secrets.VERCEL_TOKEN }}

      - name: Deploy
        run: vercel deploy --prod --yes --token=${{ secrets.VERCEL_TOKEN }}
```

In `AGENTS.md`, immediately before `### Language`, insert:

```markdown
### Continuous integration

`.github/workflows/ci.yml` is the only route to production. Six jobs: `backend`, `frontend` and
`e2e` on every push, then `migrate`, `deploy-api` and `deploy-web` on `main` only, chained behind
them with `needs`.

- **The whole suite gates the deploy**, Playwright included. It is the only check that exercises
  browser to Next to FastAPI to Neon together, which is what a deploy risks
- **`pytest` and Playwright share the Neon `test` branch and both truncate it**, so they cannot
  overlap. `e2e` declares `needs: [backend, frontend]`, and one repository-wide `concurrency` group
  queues runs rather than cancelling them
- **CI migrates the `test` branch before `pytest`**, so a commit carrying a new migration is not
  tested against a stale schema, and every migration is applied to a throwaway database before
  production sees it
- **Migrations run before the backend deploys**, which means a migration must leave the currently
  deployed code working. Add columns, do not rename or drop them in the same commit that stops
  using them
- **The backend deploys before the frontend**, so a changed API contract exists before anything
  calls it
- **Vercel's Git integration is disconnected on both projects.** Left on, every push would deploy
  twice: once immediately and ungated, once through this pipeline
- The API key, login password and auth secret used in CI are literals in the workflow file. The
  services they protect are local to the runner and die with the job
```

- [ ] **Step 3: Add the deferred decisions**

In `AGENTS.md`, at the end of `## Deferred decisions`, append:

```markdown
- **Vercel builds remotely, from CI.** Actions calls `vercel deploy --prod` rather than building
  locally and pushing with `--prebuilt`. Building locally would mean `vercel pull` writing `.vercel/`
  for two projects that both deploy from the repository root, and compiling a Python function on a
  runner, to move build minutes off Vercel. If build feedback ever needs to be faster than a remote
  build, `--prebuilt` is the change.
- **One Neon `test` branch, shared and serialised.** `pytest` and Playwright both truncate it, so the
  pipeline runs them in sequence behind a single repository-wide concurrency group. Two branches
  would let them run at once and cut a couple of minutes off every push; one branch is one fewer
  thing to keep migrated.
- **The Vercel CLI is not pinned in CI.** `npm install -g vercel@latest` means a CLI break shows up
  as a failed deploy rather than a bad one, which is the right failure to take unattended. Pinning
  the major in that one step is the fix if it ever happens.
```
