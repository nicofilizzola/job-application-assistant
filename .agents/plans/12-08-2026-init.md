# Job Application Assistant - Build Plan

Created 2026-08-12. Spec: `AGENTS.md`.

Ends with two Vercel projects live, real data imported, all suites green.

## Decisions taken before planning

| Question   | Answer                                                  |
| ---------- | ------------------------------------------------------- |
| Back-end   | FastAPI, separate `backend/` folder                     |
| Topology   | BFF - browser talks only to Next; Next talks to FastAPI |
| Hosting    | Two Vercel projects, one repo                           |
| Database   | Nothing provisioned yet; Phase 0 creates it             |
| CSV import | Run during the build against a Neon dev branch          |
| Done when  | Deployed, live URL, smoke-tested                        |

## Steps needing your keyboard

Interactive logins cannot be done for you. They are all in Phase 0 except the last deploy.

- `vercel login`
- Neon provisioning via the Vercel marketplace (browser flow)
- Choosing the real `APP_PASSWORD`

Everything else runs unattended.

## Phase 0 - Provisioning

No code. Get credentials in place so nothing later blocks on them.

1. `npm i -g vercel@latest`, then **you run** `vercel login`.
2. **You run** `vercel integration add neon` and complete the browser flow. Create a project named
   `job-application-assistant`.
3. In the Neon console create a branch named `dev` off `main`. `dev` is what the build and the test
   suite point at; `main` stays clean until Phase 9.
4. Capture both connection strings. Use the **pooled** endpoint (`-pooler` in the host).
5. Generate secrets: `openssl rand -base64 32` twice, for `AUTH_SECRET` and `BACKEND_API_KEY`.
6. Choose `APP_PASSWORD`.

Success criteria:

- [x] `vercel whoami` returns your account
- [x] Neon project exists with `main` and `dev` branches
- [x] `psql "$DATABASE_URL" -c 'select 1'` succeeds against the `dev` pooled URL
- [x] All five secret values recorded somewhere you can retrieve them
- [x] Nothing secret is in the repo

Phase 0 outcome, 2026-08-13:

- The Neon project holds two branches: `main` (default) and `dev` branched off it. This repo is
  public, so the project id, org id and endpoint hostnames are deliberately not written down here -
  `neonctl projects list` and `neonctl branches list` are the source of truth.
- `AUTH_SECRET`, `BACKEND_API_KEY`, `APP_PASSWORD` live as non-sensitive env vars on the
  `job-application-assistant` Vercel project across all three environments; `vercel env pull` reads
  them back. The `dev` connection string comes from
  `neonctl connection-string dev --project-id <id> --pooled`.
- `psql` is not installed locally; connectivity was verified with `psycopg`, the driver the backend
  uses.
- Carry into later phases: the Neon resource is connected to `job-application-assistant`, so
  `DATABASE_URL` there points at `main`. Phase 1/2 must write the **`dev`** URL into `backend/.env`
  rather than trusting `vercel env pull`, and Phase 9 must keep `DATABASE_URL` off the frontend
  project.

## Phase 2 - Back-end foundation

A running FastAPI service with auth and config, before any database work.

1. `backend/pyproject.toml`: `requires-python = ">=3.13"`, `[tool.vercel] entrypoint = "app.main:app"`,
   deps `fastapi`, `pydantic`, `pydantic-settings`, `sqlalchemy`, `psycopg[binary]`, `alembic`;
   dev deps `pytest`, `httpx`, `ruff`.
2. `app/config.py` - `pydantic-settings` reading `DATABASE_URL` and `BACKEND_API_KEY`. Fail loudly at
   startup if either is missing.
3. `app/security.py` - a dependency comparing `X-API-Key` with `compare_digest`, raising 401.
4. `app/main.py` - the FastAPI instance and `GET /health`, which is the one route with no API key.
5. `ruff` config: line length 100, import sorting on.

Success criteria:

- [ ] `uv run fastapi dev app/main.py` starts clean
- [ ] `GET /health` returns 200 with no header
- [ ] A protected probe route returns 401 with no key, 401 with a wrong key, 200 with the right one
- [ ] Deleting `BACKEND_API_KEY` from env makes startup fail with a readable message, not a stack trace
- [ ] `uv run ruff check .` and `ruff format --check .` pass

## Phase 3 - Data layer

1. `app/db.py` - engine with `NullPool` (serverless: connections cannot be reused), `sessionmaker`,
   and a `get_session` dependency that commits on success and rolls back on exception.
2. `app/models.py` - `Application` and `StatusUpdate` exactly as specced. `uuid` PKs with server-side
   defaults, `rating` as `REAL`, `date` as `Date` not `DateTime`, cascade delete on the relationship
   **and** on the FK constraint.
3. `alembic init`, configured to read `DATABASE_URL` from env rather than `alembic.ini`.
4. First migration: both tables plus the `(application_id, date desc, created_at desc)` index.
5. Apply to the `dev` branch.

Success criteria:

- [ ] `alembic upgrade head` succeeds against `dev`
- [ ] `alembic downgrade base` then `upgrade head` succeeds - the migration is reversible
- [ ] `\d status_updates` shows the composite index with both `DESC` orderings
- [ ] Deleting an application row via raw SQL removes its status updates
- [ ] Inserting `rating = 4.5` reads back as exactly `4.5`, not `4.5000001` or a string

## Phase 4 - API

The derived-status query is the one genuinely tricky piece here.

1. `app/schemas.py` - Pydantic models. `ApplicationListItem` carries `current_status` and
   `last_update_date`; `ApplicationDetail` carries the full timeline. `Status` is a `StrEnum` of the
   six values, so an invalid status is a 422 rather than a bad row.
2. `app/routers/applications.py` - the seven routes from AGENTS.md.
3. The list query: one `select` with a lateral join onto the latest update per application, ordered
   `date DESC, created_at DESC`, with `include_closed=false` filtering out `Rejected`/`Withdrawn` in
   SQL.
4. `POST /applications` opens a transaction and writes the application plus its first status update
   together.
5. `scripts/export_openapi.py` writing `backend/openapi.json`, so type generation never needs a
   running server.

Success criteria:

- [ ] All seven routes reachable, all requiring `X-API-Key` except `/health`
- [ ] **Same-date tiebreak**: two updates sharing a date, the later `created_at` wins. Tested both
      insertion orders so a coincidentally-correct ordering cannot pass
- [ ] The list endpoint issues **one** query regardless of row count, asserted by counting statements
      via a SQLAlchemy event listener - not by eyeballing logs
- [ ] A failed status-update insert inside `POST /applications` leaves **no** orphaned application row
- [ ] `include_closed=false` excludes exactly the closed statuses; `true` returns everything
- [ ] List is ordered most-recently-updated first
- [ ] 404 on unknown id for GET, PATCH, DELETE
- [ ] `DELETE /applications/{id}` removes its updates
- [ ] Rating outside 1-5, or not on a 0.5 step, is rejected with 422
- [ ] `pytest` green; contract tests run through `ASGITransport` with no network

## Phase 5 - CSV import

Parser and its tests first, then run it. The script reports what it could not parse; it never guesses.

1. `scripts/import_csv.py` using the stdlib `csv` module - the file has quoted newlines and splitting
   on `\n` corrupts it.
2. Date normaliser handling every observed format: `7 Jul 2026`, `08 Jul`, `9 July`, `17/Jul`,
   `27/July`, `12/Aug`, `11 Aug`, `30/07`, `11/08`, and lowercase variants. Year absent means 2026.
3. `Etat` mapping: `Contact reçu`→Contacted, `Envoyé`→Applied, `1E`/`2E`→Interview,
   `Refus direct`→Rejected, `No après 1E`→Interview **then** Rejected.
4. Timeline extraction: leading `<date> - <text>` and `<date> <text>` only. Unmatched text stays in
   the comment. Extracted updates inherit the row's `Etat`-derived status - **never** infer status
   from prose.
5. Fix `Cosulting`→`Consulting`. Append unnamed column 11 to the Castel Afrique comment. Store links
   verbatim, tracking params and all.
6. Print a report of everything ambiguous.
7. Run against `dev`.

Success criteria - parser unit tests:

- [ ] Every date format above maps to the right 2026 date
- [ ] The 7 expected extractions are found, and no others:
      SalesForce `22/jul - ajouté recruteuse...`; mc2i `27/july`, `30/july`, `06/aug`;
      Smoteo `30/07 premier appel...`; Alpine `11/08 appel avec sara turgeman...`;
      Swissquote `11 aug - update...`
- [ ] Mid-sentence dates are **not** extracted - Keyteo's `entretien le 29/07` and Castel Afrique's
      `entretien le 29/07 avec Quentin` stay in the comment
- [ ] `No après 1E` produces two updates, Interview before Rejected
- [ ] A row whose comment is entirely unparseable keeps the comment intact and still gets its one
      guaranteed update

Success criteria - the actual run:

- [ ] **26** applications, 0 rows skipped
- [ ] Every application has at least one status update
- [ ] **8** applications resolve to a closed status
- [ ] Multi-line company `Morgan Phillips Recruitment. / Castel Afrique` survives as one string
- [ ] `Alpine Consulting (client: SICPA)` is unsplit
- [ ] No sector reads `Cosulting`
- [ ] The Castel Afrique comment ends with the column-11 research text
- [ ] The report explicitly flags ThoughtLabs (`I'm no longer interested` implies Withdrawn but is
      not inferred) and the two un-extracted mid-text dates
- [ ] Re-running against a clean database produces identical counts

## Risks

**Cold starts on a two-hop path.** Browser → Next → FastAPI, both serverless. The first request after
idle pays both. Expected, and fine for one user; if it grates, cache in the Next layer rather than
letting the browser reach FastAPI directly.

**`NullPool` is not optional.** Neon's pooled endpoint plus `NullPool` is the combination that works
in serverless. Any other pairing works locally and exhausts connections in production - which is why
Phase 9 smoke-tests against real production rather than trusting the local run.

**Generated types drift.** `openapi.json` is committed. Change Pydantic without regenerating and
TypeScript keeps compiling against a schema that no longer exists. Phase 6's no-diff check is what
catches it.

**Import is destructive if re-run.** It assumes an empty database. Running it twice doubles
everything. It runs exactly twice by design - once on `dev`, once on `main` - and is deleted after.
